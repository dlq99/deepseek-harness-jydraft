# 01 · 上游隔离策略

> 这份文档纠正了我此前的建议。**我先前说「配 upstream remote 是第一要务」——那是错的**，
> 因为我默认了你会跟上游合并。你说不想被打扰，那正确做法相反。

---

## 0. 结论

**不加 `upstream` remote。** 但要**记录 fork point**，并让隔离**可自动检查**。

| 做什么 | 为什么 |
|---|---|
| ❌ **不配 upstream remote** | 不配就没有任何自动 fetch，`git status` 不会被上游的变动打扰 |
| ✅ **记录 fork point**（`jydraft/FORK_POINT`） | 没有它，你连「我改了什么」都算不出来 |
| ✅ **`jydraft/` 之外必须与 fork point 一致** | 这条让「按需拉上游修复」这个选项保持**便宜** |
| ✅ **自动检查**（`check-isolation.mjs`） | 隔离是**每天要维持的状态**，不是一次性决定 |

**为什么「记录 SHA」和「配 remote」是两件事**：remote 只是**便利**，SHA 才是**能力**。
你留着 SHA，任何时候想拉上游，加一行 remote、fetch、用完删掉——十秒的事。
而如果不记录 SHA，你就永远算不清自己偏离了多少。

---

## 1. 隔离的定义

> **`jydraft/` 之外的任何文件，都必须与 fork point 一模一样。**

我们所有的东西都在 `jydraft/` 一个目录里。这条有两个好处：

1. **diff 可读**：`git diff <fork-point>..HEAD` 只显示 `jydraft/` 下的内容。一眼能看完自己改了什么。
2. **上游升级便宜**：因为没碰它的代码，把基线换到更新的上游 commit 时，冲突面**理论上是零**。

**自动检查**：

```sh
node jydraft/scripts/check-isolation.mjs
```

它查三件事：fork point 记录有效 · `jydraft/` 外没有未提交改动 · 相对 fork point `jydraft/` 外没有已提交改动。

**当前状态**（写这份文档时）：

```
fork point: 477b4f4205 2026-09-24 Merge pull request #5180 from deepseek-harness/rel/dsh-0.1.7-rc.2
工作树:     只有未跟踪的 jydraft/  —— 零分叉
```

## 2. 为什么「不跟上游」对你更合适

我此前把「198 次/天」当成威胁。**它只在「你要合并」时才是威胁。** 你选择不跟，那这个数字对你就变成零成本。

| | 跟上游（合并/变基） | **隔离（本策略）** |
|---|---|---|
| 上游 198 次/天 | 你每天要处理冲突 | **你不用看它** |
| 拿 bug 修复 | 自动来 | **按需拉**（见第 4 节） |
| 拿新能力 | 自动来 | 按需拉，或自己写 |
| 你的改动量 | 越大越痛 | 只有 `jydraft/`，**很小** |
| 风险 | 合并冲突 | **你拿不到上游的修复** |

**代价是诚实的**：你拿不到上游的修复与新增能力。但这个代价**是可选的**——需要时按第 4 节拉一次。
反过来，如果配了 remote 又忍不住去看，那你就是在承担「合并」的成本而没拿到「按需」的灵活性。

**一句话**：隔离把上游从「持续的干扰源」变成「一个随时可以打开、也可以永远不打开的抽屉」。

---

## 3. 为什么「不改 `packages/`」不只是洁癖

我此前说「核心不进 DSH」是架构理由（R6：不要与宿主耦合）。**在 fork 语境下还有第二条更硬的理由**：

> **一旦你改了 `packages/`，第 4 节的「按需拉取」就可能冲突。**

上游的修复往往落在你改过的同一个文件里。隔离状态下 cherry-pick 是干净的；破坏隔离后，你每拉一个修复都要先解一次冲突——**于是你就不会拉了**，于是你就永久失去了上游。

**所以「不改源码」不是道德要求，是让一个选项保持可用的工程手段。**

**如果确实需要改 `packages/` 里的东西**，正确顺序是：

1. **先问能不能用扩展点做到**（`jydraft/docs/02-*` 里有逐条对照：界面 / 行为规范 / 信息注入都有官方扩展点）
2. 如果扩展点做不到，**先给上游提 issue 或 discussion**——如果它对框架有价值，你会得到一个可升级的实现，而不是一处永久分叉
3. 只有「扩展点做不到 + 上游不要 + 确实必需」三条同时成立，才改 `packages/`，**并且把这次改动的理由写进 `jydraft/docs/`**

## 4. 按需拉取：什么时候拉、怎么拉

### 4.1 什么时候值得拉

只在这两种情况：

| 情况 | 例子 |
|---|---|
| **上游修了一个你正踩着的 bug** | 你的插件在某个版本上崩，上游已修 |
| **上游加了一个你正要自己写的功能** | 你准备写「阶段会话自动归档」，发现上游刚加了生命周期事件 |

**其它情况一律不拉。** 尤其不要「顺手更新一下」——那是把隔离的好处白扔掉。

### 4.2 怎么拉（cherry-pick 单个 commit，不是 merge）

**关键**：你要的是**一个修复**，不是 198 天 × 198 次/天的全部历史。所以 **cherry-pick，不 merge。**

```sh
# ① 临时加 remote（用完删）
git remote add upstream-tmp https://github.com/deepseek-ai/deepseek-harness.git
git fetch upstream-tmp --no-tags

# ② 找到你要的那个 commit
git log --oneline upstream-tmp/main -- packages/<你要的组>/

# ③ 只摘那一个
git cherry-pick <sha>

# ④ 立刻删掉 remote，恢复「不被打扰」
git remote remove upstream-tmp
```

**cherry-pick 之前先做一次隔离检查** —— 如果隔离已破，这一步会冲突，先解决隔离问题。

**cherry-pick 之后**：

```sh
node jydraft/scripts/check-isolation.mjs   # 会报「jydraft/ 之外有改动」
```

**这是预期的** —— 你刚刚故意把上游的一个 commit 摘进来了。此时要做的是**更新 fork point 的语义**：
在 `jydraft/docs/` 里记一条「哪天摘了哪个 commit、为什么」。**不要改 `FORK_POINT` 文件**（它记的是分叉点，不是当前状态）。

### 4.3 换基线（大版本升级）

比 cherry-pick 更大的动作：把整个 fork 挪到一个更新的上游 commit 上。**因为隔离，这一步理论上是干净的**：

```sh
git remote add upstream-tmp https://github.com/deepseek-ai/deepseek-harness.git
git fetch upstream-tmp --no-tags
git rebase --onto upstream-tmp/<新的ref> <旧的fork-point> master
# 冲突应该只在 jydraft/ 里（如果有）
git remote remove upstream-tmp
# 换基线后更新 FORK_POINT 与本文第 1 节的记录
```

**这条之所以可行，完全是因为隔离**。如果不隔离，`rebase --onto` 会在几百个文件上冲突。

## 5. 破坏隔离之后怎么办

`check-isolation.mjs` 报错时，三个选项：

| 选项 | 什么时候 | 怎么做 |
|---|---|---|
| **撤回** | 改动是误操作或试错 | `git checkout <fork-point> -- <文件>` 还原 |
| **搬进 `jydraft/`** | 改动其实可以做成插件或配置 | 最常选。重写成插件/扩展点，还原 `packages/` |
| **接受分叉** | 确实必须改框架内部 | 在 `jydraft/docs/` 写一条决策记录（改了什么、为什么扩展点做不到、上游有没有相关讨论），并知道第 4 节的 cherry-pick 从此可能冲突 |

**默认选第二个。** 因为绝大多数「必须改源码」的直觉，最后都发现扩展点能做——这是本工作区前几轮调研的结论（界面 / 行为规范 / 信息注入三类改造，逐条都有官方扩展点）。

---

## 6. 日常怎么做

```sh
# 提交前
node jydraft/scripts/check-isolation.mjs

# 想知道自己改了多少
git diff 477b4f420553e8a52c2fbccc464d7561b239c443 --stat

# 想确认没被上游打扰
git remote -v      # 应该只有 origin
```

**`git remote -v` 只有 `origin`（你自己的 fork）** —— 这是本策略的**预期状态**，不是配置缺失。
